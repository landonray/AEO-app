# Luminaire — Build Plan

This plan breaks the refined spec (`docs/specs/aeo-app-refined.md`) and the QA plan
(`docs/specs/aeo-app-qa-plan.md`) into ordered chunks. The worktree currently has only
docs — there is no `package.json`, no `src/`, nothing scaffolded. Every chunk creates or
extends files that did not previously exist.

Ordering philosophy:

1. Project scaffolding first (so any later chunk can `npm install` and run).
2. Tight, dependency-free leaf modules (types, schema, theme, utils, db client).
3. Pure-logic libraries (parser, classifier, metrics, gateway/perplexity/google-aio clients,
   scraper, generators). These are mostly independent and the strongest place to fan out
   work in parallel.
4. Queries + orchestrator stitch the leaves together.
5. API route handlers — each route is its own file, so route chunks can run in parallel
   once their underlying lib chunks are done.
6. UI primitives, charts, dashboard shell.
7. Per-tab UI built on the shell, plus onboarding wizard, plus the setup page and the
   root-page entry router.
8. README + cron documentation last.

Tests live in the same chunk as the code they cover (per the QA plan): unit tests for
parser/metrics/classify/utils/clients, integration tests for queries/orchestrator/routes,
Playwright for onboarding + dashboard tabs.

The biggest parallel-runnable batches are:
- Chunks **2, 3, 4, 6** can all run together after Chunk 1.
- Chunks **9, 10, 11, 12** (the LLM/SERP/scraper clients) can all run together after Chunk 2.
- Route chunks **17, 18, 19, 20, 21, 22** can run together once their lib deps are done.
- Tab UI chunks **26, 27, 28** can run together once the shell (25) and the APIs they call are done.

## Chunk 8: Response parser
- Files: src/lib/llm/parser.ts, src/lib/llm/__tests__/parser.test.ts
- QA Scenarios: §3.1 brand mention, §3.2 position score, §3.3 sentiment, §3.4 competitor mentions, §3.5 citation extraction, §3.6 (classifier integration only)
- Dependencies: 2, 5, 7
- Complexity: large

This is the metric-fidelity center of gravity for the product. Implement five pure
functions taking `(responseText, brand, competitors)` and `(apiCitations)`:

1. `detectMentioned(text, brand)` per §11.1 — case-insensitive word-boundary match on
   the regex-escaped brand `name` OR an apex match on `brand.domain` after
   `normalizeDomain`. Multi-word names allow internal whitespace flex.
2. `computePositionScore(text, brand)` per §11.2 — numbered-list rule (line starts with
   `/^\s*(\d+)[.)]\s/`), capped at 5; otherwise 5-equal-segment math; NULL if not
   mentioned. Returns `number | null`. First mention wins (§17 / QA 3.2.h, 3.2.j, 18.4).
3. `computeSentiment(text, brand)` per §11.3 — sentence split on `/[.!?]+\s+/`, keep
   brand-bearing sentences, count positive/negative words from the §11.3 lists
   (word-boundary, case-insensitive). Tie or both-zero → `neutral`.
4. `computeCompetitorMentions(text, competitors)` per §11.4 — same name-OR-domain rule;
   returns `{ [competitorName]: boolean }` with one entry per competitor in the input
   list (display name as key, not domain or id).
5. `extractCitations(text, apiCitations)` per §11.5 — regex
   `https?:\/\/[^\s\)\]\}"'<>]+` on the prose, strip trailing `.,;:!?`, union with the
   supplied API URL list, dedupe by full URL.

Lock the word lists from §11.3 as constants inside the module so test failures surface
deliberate edits. Tests follow the QA tables row-by-row; lock the empty/zero behaviors
called out in §17.

## Chunk 9: LLM Gateway client
- Files: src/lib/llm/gateway.ts, src/lib/llm/__tests__/gateway.test.ts
- QA Scenarios: §4.1 request shape, §4.2 top-level content, §4.3 response_format passthrough, §4.4 JSON retry, §4.5 5xx surfaces, §4.6 60s timeout, §4.7 no secrets in errors, §14.1.c
- Dependencies: 2
- Complexity: medium

Implement `callGateway({ model, messages, max_tokens, temperature, run_id, response_format, tools, tool_choice })`
against `${LLM_GATEWAY_BASE_URL}/chat/completions` with `Authorization: Bearer ${LLM_GATEWAY_API_KEY}`.
Reads top-level `response.content` (never `choices[0].message.content` — §6 calls this
out as the streaming SSE path that does NOT apply here). Returns
`{ content, estimatedCost, runTotalCost, finishReason, toolCalls? }`.

Helper `callGatewayJSON({ ..., schema })` wraps `response_format: { type: 'json_schema', json_schema: { name, strict: true, schema } }`,
parses the content as JSON, and on failure retries ONCE with a system message prepended:
`"Return ONLY valid JSON matching the schema. No prose, no markdown."`. Second failure
throws a typed error tagged with the model.

Implement a 60s `AbortController` timeout per call (§10). Error messages must NEVER
include the bearer token (§4.7 / §14.1.c) — scrub authorization headers from any logged
error context. Unit tests use `vi.fn()` fetch mocks.

## Chunk 10: Perplexity client
- Files: src/lib/llm/perplexity.ts, src/lib/llm/__tests__/perplexity.test.ts
- QA Scenarios: §5.1 request shape, §5.2 reads choices[0].message.content, §5.3 citations fallback, §5.5 non-2xx error
- Dependencies: 2
- Complexity: small

`callPerplexity(promptText)` POSTs to `https://api.perplexity.ai/chat/completions` with
`MODEL_PERPLEXITY` (default `sonar-pro` per Q1), `max_tokens: 2000`, `temperature: 0.3`,

timeout, no cost (Perplexity doesn't return one). Tests cover the three citation
shape variants and the non-2xx error path.

## Chunk 11: Google AI Overview client
- Files: src/lib/llm/google-aio.ts, src/lib/llm/__tests__/google-aio.test.ts, src/lib/llm/__fixtures__/dfs-aio.json, src/lib/llm/__fixtures__/dfs-featured.json, src/lib/llm/__fixtures__/dfs-empty.json
- QA Scenarios: §6.1–6.6
- Dependencies: 2
- Complexity: medium

`callGoogleAIO(promptText)` POSTs to `https://api.dataforseo.com/v3/serp/google/organic/live/advanced`
with HTTP Basic (`DATAFORSEO_LOGIN:DATAFORSEO_PASSWORD`). Body is
`[{ language_code: 'en', location_code: 2840, keyword, depth: 10 }]` (US English, §8 / A5).
Response handling walks `tasks[0].result[0].items`:

1. First `type == 'ai_overview'` item — concatenate `items[*].text` (or use `markdown`),
   extract `references[*].url`.
2. Otherwise first `type == 'featured_snippet'` — use its text + references.
3. Otherwise return `{ content: null, citations: [], cost }` and record a no-mention run.

Cost comes from `tasks[0].cost` (USD); store as `estimatedCost`. Tests use three captured
fixture JSONs (one with AI Overview, one with only featured snippet, one with neither).

## Chunk 12: Web scraper
- Files: src/lib/scraper.ts, src/lib/__tests__/scraper.test.ts, src/lib/__fixtures__/homepage.html, src/lib/__fixtures__/pricing.html
- QA Scenarios: §9.1 homepage, §9.2 secondary pages (a–f), §14.5 cheerio
- Dependencies: 2
- Complexity: medium

`crawlSite(url): Promise<CrawlPages>` fetches the homepage; if non-2xx, throw a typed
`HomepageCrawlError`. Then in parallel fetches `/pricing`, `/features`, `/about`,
`/integrations`, `/use-cases`, `/product` with a 10s `AbortController` timeout each,
`User-Agent: LuminaireBot/1.0 (+https://luminaire.local)`. Non-2xx is silently skipped.
Parse with cheerio, remove `script`, `style`, `noscript`, `nav`, `footer`, `header`, then
extract `text()`. Trim and collapse whitespace. Truncate each page to 5000 characters
before returning. Output shape: `{ url, pages: { path, text }[] }` so the next chunk can
label per-URL when sending to the model. Unit tests use captured HTML fixtures and a
fetch mock.

## Chunk 13: Generators (crawl extraction, prompt, competitor)
- Files: src/lib/generators.ts, src/lib/__tests__/generators.test.ts
- QA Scenarios: §9.3 crawl extraction, §9.4 prompt generation, §9.5 competitor generation, §4.4 JSON retry surfaces here
- Dependencies: 2, 9, 12
- Complexity: medium

Three exports, each calling `callGatewayJSON` with the §9 schemas:

1. `extractCrawl(pages, url): Promise<CrawlResult>` — `MODEL_GENERATION` (gemini-2.5-flash).
   System message instructs strict JSON, no markdown. Schema has `title`, `description`,
   `category`, `targetAudience`, `coreUseCase`, `features[]`, `integrations[]`,
   `pricingInfo`, `competitorHints[]` — `pricingInfo` optional, all others required.
2. `generatePrompts(crawl, domain): Promise<{ text, topic }[5]>` — system message

   `maxItems: 5`.
3. `generateCompetitors(crawl, domain): Promise<{ name, domain }[]>` — 4–5 items, bare

   Filter out the user's own apex domain client-side.

Tests use a fetch mock at the gateway boundary; assert the request body includes the
correct schema, the response is parsed, and the JSON-retry path engages on a malformed
first response.

## Chunk 14: DB queries
- Files: src/lib/queries.ts, src/lib/__tests__/queries.test.ts
- QA Scenarios: §2.5 parameterization, §2.6 date interval, §2.7 model filter, §11 (every route's underlying queries)
- Dependencies: 2, 6
- Complexity: medium

Implement parameterized helpers on top of `lib/db.ts`. Coverage:

- Brand: `getPrimaryBrand()`, `insertBrand(input)`, `primaryBrandExists()`.
- Competitor: `insertCompetitors(brandId, rows[])`, `listCompetitors(brandId)`.
- Prompt: `insertPrompts(brandId, rows[])`, `insertPrompt(brandId, { text, topic })`,
  `listPrompts(brandId)`, `listActivePrompts(brandId)`, `archivePrompt(id)`, `getPrompt(id)`.
- Run: `insertRun(row)` returning new id, `getRuns({ brandId, days, model? })`,

- Citation: `insertCitations(runId, rows[])`, `getCitations({ brandId, days, model?, view? })`.

Rules: every value goes through positional placeholders. The model filter only adds a
`model = $n` clause when the param is provided and not `'all'` (§2.7). Date filter uses

inspect the generated SQL string + bound params (export a helper that returns
`{ sql, params }` for the test seam).

## Chunk 15: Metrics computation
- Files: src/lib/metrics.ts, src/lib/__tests__/metrics.test.ts
- QA Scenarios: §8.1–8.9 (visibility, SOV, position, sentiment-mentioned-only, change, trend, sources, URL sources, competitive rank)
- Dependencies: 2, 14
- Complexity: medium

Pure functions that take rows from `queries.ts` and return the shapes the API routes
need:

- `computeVisibility(runs)`, `computeSOV(runs, competitors)`,
  `computeAvgPosition(runs)`, `computeAvgSentiment(runs)` — **mentioned-only, returns

- `computeDomainSources(runs, citations)` and `computeUrlSources(runs, citations)` per
  §13.7 / §13.8.
- `computeCompetitiveRank(brand, competitors)` — sort by visibility desc, brand wins ties
  (§18.2 default), return 1-based index.
- `computeRankings(brand, competitors, runs)` — per-entity visibility, SOV, sentiment
  (null when zero mentions), position, change.
- `buildKeyInsight(metrics)` per the three-tier rules in §15.D.
- `buildActions(metrics, sources, rankings)` per the deterministic rules in §15.E.

Tests rely on hand-constructed `Run[]` and `Citation[]` arrays (no DB) — that's the

## Chunk 16: Orchestrator
- Files: src/lib/llm/orchestrator.ts, src/lib/llm/__tests__/orchestrator.test.ts
- QA Scenarios: §7.1–7.8 (batch, sequential, single-model failure, all-fail prompt, citation persistence, run id returned, same-shape from cron + button, no partial rows)
- Dependencies: 2, 7, 8, 9, 10, 11, 14
- Complexity: medium

`runBatch(prompts, brand, competitors): Promise<BatchResult>` drives the §10 procedure:
generate one `batchId` (UUIDv4 like `batch-<uuid>`) at the start; sequentially over
prompts and within each prompt sequentially over the five surfaces; pass `batchId` as
`run_id` to every gateway call. On per-call success: parse, classify each URL, insert
the run, insert citations. On per-call failure: structured log to `console.error`, do
NOT insert a runs row, continue. Per-call timeout of 60s comes from the underlying
clients. Returns `{ batchId, results: [{ promptId, models: [{ model, success, runId?, error? }] }] }`
plus `totalRuns`, `totalErrors`, `runTotalCost` (sum of gateway `runTotalCost` deltas
observed across the batch).

Tests run against a Neon branch with all five clients mocked at the `lib/llm/*` boundary
(import-and-spy). Confirm sequential ordering by recording call timestamps in the mocks.

## Chunk 18: Onboarding API routes
- Files: src/app/api/onboarding/crawl/route.ts, src/app/api/onboarding/generate-prompts/route.ts, src/app/api/onboarding/generate-competitors/route.ts, src/app/api/onboarding/complete/route.ts

- Dependencies: 2, 13, 14
- Complexity: medium

Four POST handlers. `crawl` validates the URL (`http://` or `https://`, prepend
`https://` if bare-domain), calls `crawlSite()` then `extractCrawl()`, returns
`{ crawlData, domain }`. `generate-prompts` calls `generatePrompts()`. `generate-competitors`

all rows (§9.6.c). Each handler validates its body shape and returns 400 on missing fields.

## Chunk 22: Cron route and cron script
- Files: src/app/api/cron/run/route.ts, scripts/cron.mjs
- QA Scenarios: §10.1 bearer auth, §10.2 active-only, §10.3 batch summary, §10.4 per-call failures stay 200, §10.5 5xx on DB failure, §10.6 cron.mjs, §14.2 constant-time
- Dependencies: 14, 16
- Complexity: small

`POST /api/cron/run` — reads `Authorization` header, compares with `CRON_SECRET` using
`crypto.timingSafeEqual` over equal-length buffers (constant-time). Anything other than
the matching bearer returns 401 with an empty body. On match: load active prompts for
the primary brand, call `runBatch`, return `{ ok, batchId, totalRuns, totalErrors }`.
Internal errors → 500. `scripts/cron.mjs` reads `CRON_SECRET` from env (fail fast if
missing), POSTs to `http://localhost:${PORT || 4810}/api/cron/run`, logs the response
counts, exits 0 on 2xx and 1 otherwise.
